From extracting text to checking it

My original application loads an image or camera capture, runs an OCR engine, displays detected regions and text, and exports results. The purpose was to explore Tesseract and EasyOCR. The saved samples include a printed receipt and a handwritten shopping list.

The shopping-list output exposes a practical problem: a detected region can still contain an incorrect transcription. In the saved EasyOCR text, “you” became “yov” and an amount written as “$2.10” became “$2,|0”. A person reusing that text needs a way to inspect and correct it before relying on it.

For this portfolio iteration, I frame the intended user as someone transcribing a short document who wants editable text and a visible source. That need is inferred from the observed errors; it has not been established through interviews.

Three decisions about trust and control
Show the source beside the editable result
Problem
Errors look plausible when text is separated from its source.
Alternatives
Text-only output; alternating image/text tabs; side-by-side review.
Choice
This new prototype places the source next to the draft on desktop and above it on mobile.
Evidence / limits
Saved errors justify making comparison possible. Reduced review time has not been measured.
Preserve the model output
Problem
Automatic corrections could silently change an amount or hide uncertainty.
Alternatives
Auto-correct; suggest corrections; let the user edit while preserving the original.
Choice
The prototype retains the original, allows manual edits, and provides undo and a confirmed reset.
Evidence / limits
The interaction is implemented in this demo. No live model confidence or suggestions are available.
Make export an explicit decision
Problem
Exporting immediately can turn an unreviewed prediction into a trusted document.
Alternatives
Immediate export; a warning; an explicit review checkpoint.
Choice
A preview and confirmation precede the download. Returning to editing clears approval.
Evidence / limits
The checkpoint is observable in the demo. It adds friction and cannot prove that the person checked every character.


What the evidence supports
The archived receipt output scored 0.00% character and word error against a visually checked reference. The handwritten list scored 9.09% character error and 63.16% word error. These two samples use different engines and are not a controlled comparison. Word error is sensitive to spacing and punctuation; the handwritten quantity “(1lb)” also needs confirmation.
A separate Python revision adds reference-based evaluation and preserves both engines' outputs. Full OCR validation remains pending because of the original environment's NumPy loading issue. This browser interaction prototype does not resolve that execution problem or introduce new accuracy results.
I used AI coding assistance for this portfolio iteration. The interface and implementation are new work; they were not part of the original coursework or evaluated by its instructor. User testing should compare successful error correction, accidental exports and perceived control against an immediate-export flow.
